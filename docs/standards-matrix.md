# ZIMDNS RFC standards matrix

**Version:** 2026-10-20 (RFC-parity ledger revision), RFC-first minimal CLI design
**Product profile:** one Zig binary, local-first authoritative DNS, controlled by a CLI; no web UI or admin socket
**Status:** normative release-profile evidence map

This matrix is the source of truth for the declared first-release profile. It separates the current repository baseline from the release target and from work that is deliberately outside the profile. A behavior is user-facing `supported` only after the linked RFC requirement, implementation path, and tests pass. A `partial` row names the subset that is actually covered; it is not a claim of full RFC conformance.

Future work is tracked outside this ledger and does not change any current row or make roadmap items user-facing capabilities; this matrix is the source of truth for the declared first-release profile.

The internal quality objective is to make the declared profile more explicit, test-backed, and safe to operate than comparable deployments. That objective is not product copy, a feature-count promise, or a claim that ZIMDNS is generally superior to another DNS server.

## Status vocabulary

| Status | Meaning | Evidence needed |
|---|---|---|
| `supported` | Implemented for the declared profile and safe to advertise. | RFC section, implementation path, and passing unit/golden/integration tests; malformed-input coverage where applicable. |
| `partial` | Only the named subset is implemented. | Tests cover the named subset and the missing behavior is stated. |
| `planned` | Roadmap intent; not a user-facing capability. | A roadmap item and proposed test linkage. |
| `not-applicable` | The RFC does not define behavior for this DNS-only server. | An RFC-scope rationale; no implementation claim. |
| `out of scope` | Deliberately excluded from this profile. | Rationale and, when useful, a pointer to a later research item. |

RFC 9520 ("Negative Caching of DNS Resolution Failures", a Standards Track document that updates RFC 2308, RFC 4035, and RFC 4697) is `partial` here. What the profile implements is what RFC 9520 §2 leaves intact: NXDOMAIN and NODATA are not resolution failures, so they are cached under the RFC 2308 §3/§5 negative-TTL rule and cut below a cached denial by the RFC 8020 §3.2 descendant rule, and the §3.1 retry bound is met, because the forwarder makes two UDP attempts per upstream and retries a truncated answer over TCP, which §3.1 allows as a different transport. §3.2's MUST is now implemented — "Resolvers MUST implement a cache for resolution failures": an upstream SERVFAIL, an upstream REFUSED, an upstream FORMERR, and an unreachable upstream are held in a bounded 64-entry failure cache beside the answer cache, the next client for the same question is answered from it with the same RCODE and without a new upstream query, the entry expires on its own after the operator's `minimum-failure-cache-time` seconds (default 5, inside §3.2's one-second floor and five-minute ceiling), and a cached failure is never answered as an NXDOMAIN or a NODATA and never sets AD. §3.4's MUST to cache DNSSEC validation failures is implemented as well: a validation failure is held in the same bounded failure cache with the SERVFAIL RCODE and the RFC 8914 DNSSEC-bogus code the validator produced, and the next client for the same question is answered from it with the same RCODE and the same code and without a new upstream query. What is still open is §3.2's backoff SHOULD, which the fixed cache time does not implement, and RFC 4035 §4.7's restriction, which §3.4 keeps with its "with some restrictions" wording, that a resolver SHOULD answer from a cache of validation failures only after the number of failures for that question exceeds a threshold; the negative answers and cache row above records the same boundary.
