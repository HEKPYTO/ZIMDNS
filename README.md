# ZIMDNS

ZIMDNS is a minimal, local-first DNS server and CLI written in Zig. The current profile is one scriptable binary with a small authoritative path, safe DNS/UDP and DNS/TCP transport, and a standards matrix that names the exact evidence behind every advertised behavior. There is no web UI or remote administration surface in this profile.

The [RFC standards matrix](docs/standards-matrix.md) is the source of truth for what is `supported`, `partial`, `planned`, `not-applicable`, or `out of scope`. A roadmap item is not a supported feature, and a `partial` row names only its tested subset.

The internal quality goal is to make this declared profile explicit, test-backed, and safe to operate. Any comparison with a comparable DNS server is an internal measurement target, not product copy or a general superiority claim. The immutable comparison source is the [a comparable DNS server `SupportedRFCs.md` inventory at commit ``]().

## Current status

The repository contains the bounded authoritative and forwarding profile. It currently has DNS message/name/RDATA parsing, continuous authoritative UDP listeners, a DNS/TCP ingress with at most 16 frames per connection, opt-in forwarding with source/ID/question checks and a TC-to-TCP upstream retry only where upstream TCP deadlines are available (TC fails closed otherwise), a 64-entry in-memory cache of positive and negative answers with a 24-hour serve-stale window that opens only after an upstream failure, and a bounded failure cache for the resolution failures: the time a failure is held doubles with every consecutive failure of the same question, from the operator's `minimum-failure-cache-time` seconds up to RFC 9520's five-minute ceiling, and a question that resolves again starts again at the operator's minimum, extended DNS error diagnostics on the forwarding path and on a blocklist refusal, opt-in DNS Cookie validation, opt-in DNS64 synthesis, a CLI query client, and strict configuration/zone/blocklist parsers. A response that must be shortened drops its EDE option before any other data and sets the truncation bit (RFC 8914 §3). The two ingress transports run the same dispatch, so a forwarding question that arrives over TCP is answered by the forwarder exactly as the same question over UDP is (RFC 9210 §3). The operator sets the two connection limits RFC 9210 §4.2 allows a server to configure: `tcp-max-connections-per-source <count>` closes a connection from a source that already holds that many, and `tcp-max-connection-duration <seconds>` closes a connection that has lived that long, idle included. Without either directive the project's own bounds hold. Forwarding is disabled unless both an explicit recursion ACL and a forwarder are configured; consult the matrix for each exact boundary and its evidence. The encrypted transports are reachable one at a time: `--serve-dot` serves DNS over TLS (RFC 7858) once the operator opts in with `--enable-encrypted-dns` and names a certificate and key, and the port speaks only the `dot` ALPN token, so it never answers a cleartext DNS frame; `--serve-doh` serves DNS over HTTPS (RFC 8484) over the same TLS server, with the `http/1.1` ALPN token and the RFC 8484 GET and POST mapping, so that port never answers a cleartext HTTP request either; `--serve-xfr` serves zone transfers over a strict-TLS session (RFC 9103), with the `dot` ALPN token and TLS 1.3, so a secondary can pull an AXFR or IXFR over an encrypted channel and that port never answers a cleartext transfer.

A referral carries the glue of the delegation's name servers that the zone holds: the in-domain name servers of RFC 9471 §3.1 and the sibling-domain name servers of §3.2, whose names lie below the delegating zone's origin. The name servers outside that origin contribute nothing.

Locally served DNS zones (RFC 6303, RFC 6761, RFC 7793, RFC 8375) are answered by this server by default, ahead of the cache and the forwarder, so a configured upstream does not see a name reserved for private, test, invalid, loopback, or home-network use. One question is carved out of that rule: a DS question for `home.arpa` with the DO bit set is forwarded upstream, so the delegation's own denial can be proved. A configuration turns the table off with `local-zones off`, and `local-zones except <apex>` drops one apex from it. See [`examples/local-zones.gdns`](examples/local-zones.gdns) and the matrix row for the exact zone list and treatment.

A zone that carries an apex ZONEMD record (RFC 8976, type 63) is verified when it loads, and the server refuses to start if the digest does not match the zone data, naming the zone, the expected digest, and the computed one. The check accepts the SIMPLE scheme with SHA384 and SHA512; a Private Use scheme or hash algorithm is refused as unverifiable. RFC 8976 §4 steps 1 to 3 are implemented for a zone that a configured trust anchor names directly: the zone's SOA and ZONEMD RRsets must carry valid signatures chaining to that anchor, and the server refuses to start otherwise, so such a zone is never accepted on the strength of its digest alone; a zone that no trust anchor names keeps the digest-only check. §4 step 2's denial branch is implemented too: a zone that publishes no ZONEMD is resolved by the zone's own NSEC or NSEC3 proof, and an absence that no record of the zone proves is refused at startup, because absent and unknown cannot be told apart. §4 step 1's parent-side DS lookup is not implemented, because this profile reads no parent zone. `zimdns zonemd publish --zone-file <path>` computes the digest with the same code path the verifier uses and prints the record in zone text, ready to paste into the zone. See the matrix row for what is and is not implemented.

A zone is signed at startup by naming a key file in the configuration: `dnssec-key-file <path>`. Every configured zone then gets an apex DNSKEY and DS, one NSEC per authoritative owner (or, for a zone that opts into NSEC3, an NSEC3 chain), and one RRSIG per RRset (RFC 4034 §§3.1.8.1 and 5.1.4, RFC 4035 §2.3), served from memory without touching the zone file. A zone that also names a key-signing key through `dnssec-ksk-file <path>` publishes two DNSKEYs: the key-signing key carries the Secure Entry Point flag, the DS states it, it signs the DNSKEY RRset, and the zone key signs every other RRset (RFC 6781 §§3.1-3.2). The signatures are valid for 30 days, a reload refreshes them, and a zone that already carries DNSSEC records is refused rather than signed twice. ECDSA P-256 (RFC 6605 algorithm 13), ECDSA P-384 (RFC 6605 algorithm 14), and Ed25519 (RFC 8080 algorithm 15) are implemented; RSA and Ed448 are absent because the standard library has no primitive for either. `zimdns query --dnssec` sets the RFC 6891 DO bit so the server returns its signatures, and the CLI prints the answer, authority, and additional sections, which is where RRSIG and NSEC actually arrive. [`examples/dnssec/`](examples/dnssec/config.gdns) is a worked configuration.

The NSEC3 chain is opt-in, and the zone's own apex NSEC3PARAM decides it: the signer then builds one NSEC3 per owner name and per empty non-terminal, in hash order (RFC 5155 §7.1), and the authoritative path proves its denials with those NSEC3 records instead of with NSEC ones. A zone with no apex NSEC3PARAM keeps the NSEC chain. The chain is built with the iterations and salt the record states, so the RFC 9276 parameter recommendation is not enforced; only SHA-1 with the Opt-Out flag clear is implemented, and a record asking for anything else is refused.

Signing and validation are separate paths. Signing is the startup path above; chain validation runs on the forwarding path, where a configured `trust-anchor-file` gives the forwarder a static trust-anchor store of DNSKEY and DS anchors. A forwarder with no anchor file validates nothing and sets no AD. For a client that sets the DO bit and leaves CD clear, an upstream AD is cleared first, a validated-secure answer then sets AD, a bogus answer returns SERVFAIL with the RFC 8914 code, and an insecure answer is relayed without AD; when the server could not verify an answer it says why, with the RFC 8914 code for that case (Unsupported DNSKEY Algorithm (1), Unsupported DS Digest Type (2), DNSSEC Indeterminate (5), No Zone Key Bit Set (11)), which rides on the answer the client still gets and on the cached copy of it. Validation runs before the answer is cached, so a bogus answer is never stored. The matrix names what is still missing: key rollover, RFC 5011 automated rollover of the trust anchors, RSA, Ed448, iterative recursion, and root priming — the forwarder sends the full QNAME to its configured recursive upstream.

A request can be authenticated with TSIG (RFC 8945): `tsig-key-file <path>` names the key file, the server verifies the request's MAC and signs its answer with the same key and algorithm. The key file takes the five RFC 8945 §6 HMAC-SHA algorithm names and the three truncated names of RFC 4868 §2.6, and one key name may carry several of them. The file is re-read on SIGHUP, so a key can be added, changed, or removed without a restart; a key file that is missing, unreadable, or malformed at reload time is reported on stderr and leaves the served keys in place, while a malformed key file still stops the server at startup.

Two EDNS(0) options this server answers are configuration directives, and neither is ever sent to a client that did not ask for it. `nsid <hex>` (RFC 5001 §2.3, option code 3) answers a resolver's NSID request with the operator's own identifier, written in the two-hex-digits-per-octet presentation format the RFC requires; nothing is derived from an address or a hostname, so a server with no `nsid` line answers no NSID at all. `zoneversion on|off` (RFC 9660, option code 19) answers a ZONEVERSION request with the responding zone's SOA serial — TYPE 0, or SOA-SERIAL — for answers, NXDOMAIN, NODATA, and referrals alike; it is on by default, and a malformed request is answered FORMERR as §3.2.1 requires. One more EDNS(0) option is a behavior and not a directive: RFC 7314's EXPIRE (option code 9) is answered with the zone's SOA EXPIRE value when the query carries the zero-length option, and a server that is not authoritative for the zone never adds it. A second behavior and not a directive: RFC 7828's edns-tcp-keepalive (option code 11) is answered on a TCP session with the idle timeout this server applies to that session, and the option of a UDP query is ignored as §3.3.1 requires.

A third directive is not an EDNS option: `minimal-any-ttl <seconds>` (RFC 8482 §4.2) sets the TTL of the synthesized HINFO returned for a minimal `QTYPE=ANY` answer; it defaults to 86400 seconds and may be any unsigned 31-bit value. `minimal-any-ttl-tcp <seconds>` sets the same TTL for a question that arrived over TCP (RFC 8482 §4.4) and defaults to the value of `minimal-any-ttl`.

One EDNS(0) option is sent without being asked for: RFC 9567's Report-Channel (option code 18) names the agent domain a client may send error reports to. `error-report-agent <domain>` sets it, the name is folded to lower case and completed with its trailing dot, and a value that is not a domain name stops the server at startup. The option rides in the OPT record of an authoritative answer, so it appears only where the query carried EDNS(0) and the server is authoritative for the name: a refusal and a referral carry none. The root domain is never advertised (§4), and the option is left out of the answers of a zone that holds the agent domain, because §8.1 forbids an agent domain that is a subdomain of the domain the server reports on.

The IXFR delta log (RFC 1995) lives in memory unless the operator names a file for it: `ixfr-journal-file <path>` writes every serial transition and the records that changed to that file and reads it back at startup, so an IXFR client that asks for a serial from before a restart is still answered incrementally. A SIGHUP re-reads the zone file, and the reload computes the records that changed, so the answer is RFC 1995 §4's difference sequence: the current SOA, then the deleted records with the older SOA opening them, then the added records with the newer SOA opening them, then the current SOA again. A zone file that does not parse, or that carries no newer serial, leaves the served zone in place. A journal file in the old format, which holds the serial pair alone, is still read without failing, and a client at one of those serials gets the full transfer. A corrupt or truncated line in the file is skipped and the server still starts.

The forwarding path forwards the client's EDNS Client Subnet option (RFC 7871) upstream and answers the client with the scope the upstream reported. The operator's `client-subnet-max-prefix <length>` trims the client's source prefix to that many bits before the query goes upstream (RFC 7871 §7.1.1), and `forwarder-deny-port <port>` or `forwarder-deny-port <first>-<last>` keeps the forwarder's outgoing queries off the source ports the operator names: the socket is closed and another one bound until a port outside the list is found, and the query fails when there is none.

RFC 6147 address synthesis is opt-in on the forwarding path: `nat64-prefix <prefix> [<ipv4-range>]` names the operator's NAT64 prefix and the IPv4 range it serves, and `dns64-exclude <ipv6-prefix>` adds a range to the exclusion set of §5.1.4. An AAAA question whose upstream answer is empty is answered with one AAAA per A record of the same name, the IPv4 address embedded in the prefix as RFC 6052 §2.2 requires; an answer that carries a CNAME or DNAME chain is followed to the owner that holds the A records, and the chain stays in the answer beside the synthesized record. A name with a real AAAA is never synthesized over, an AAAA inside the exclusion set is not real AAAA data and is dropped, and the synthesized record carries the A record's TTL capped by the zone's SOA. Without a configured prefix nothing is synthesized, which is a departure from RFC 6147 §5.2's Well-Known Prefix default.

A forwarder configured with `trust-anchor-file` also signals its anchors' Key Tags on its own upstream DNSKEY queries (RFC 8145 §4.2, option code 14) and never answers with that option. The bundled `query` CLI prints an OPT pseudosection for any answer that carries an OPT record, rendering ZONEVERSION's TYPE 0 as `SOA-SERIAL <serial> (<zone>.)` and NSID as hexadecimal (RFC 9660 §2.2, RFC 5001 §2.4), and printing any other EDNS option as its code and length. `--zoneversion` and `--nsid` ask for those two options; `--dnssec` sets the DO bit instead, which is a different request. `--0x20` randomizes the case of the first letter of every label of the question name, drawing each case from the standard library's CSPRNG, and the CLI then prints the question the server echoed, with the case it used. The mechanism comes from the expired Internet-Draft draft-vixie-dnsext-dns0x20 and is no RFC requirement, so it is off unless the operator asks for it. A zone file's own spelling reaches the wire: the owner name of a served record and the names inside its RDATA keep the case the zone file wrote them in, because RFC 4343 §4.1 does no case conversion on output, while the signature and the ZONEMD digest are made over the canonical lowercase form of RFC 4034 §6.2, so a zone written in upper case and the same zone written in lower case digest the same.

RFC 9463 DNR is `not-applicable` to this DNS-only server because it defines DHCP/Router Advertisement provisioning; no DHCP, RA, parser, or output artifact is provided.

## Command line

`zimdns --help` (or `-h`) prints the usage, and `zimdns --version` the build version. The flags the three commands take:

| Command | Flags |
| --- | --- |
| `zimdns server run` | `--config <path>`, `--zone-file <path>`, `--once-udp [port]`, `--once-tcp [port]`, `--serve-udp`, `--serve-tcp`, `--serve-dot`, `--serve-doh`, `--serve-xfr`, `--enable-encrypted-dns`, `--tls-cert-file <path>`, `--tls-key-file <path>`, `--max-queries <count>`, `--max-requests <count>`, `--print-metrics` |
| `zimdns query` | `@<server>`, `-p <port>`, `--tcp`, `--dnssec`, `--zoneversion`, `--nsid`, `--0x20` |
| `zimdns zonemd publish` | `--zone-file <path>`, `--scheme <code>`, `--hash <code>` |

`--once-udp` and `--once-tcp` serve a bounded number of queries and exit, `--serve-udp`, `--serve-tcp`, and `--serve-dot` keep serving, `--max-queries` sets the one-shot bound where `--max-requests` sets the serving one, and `--print-metrics` prints the Prometheus counters when a UDP run ends. `--serve-dot` needs `--enable-encrypted-dns` and `--tls-cert-file` and `--tls-key-file`; the certificate and key are loaded before the port is bound, so a broken identity refuses the run and leaves no port open. `zimdns query` asks `@<server>` on `-p <port>` for a name and a type, over DNS/UDP, or over DNS/TCP with `--tcp`. `zimdns zonemd publish --zone-file <path>` computes the RFC 8976 digest of a zone file and prints the record in zone text; `--scheme` and `--hash` take the registry codes, where scheme 1 is SIMPLE, hash 1 is SHA384 and hash 2 is SHA512.

## Development

```sh
zig fmt .
zig build
zig build test
zig build test-golden
zig build test-config
zig build test-fuzz
zig build test-integration
zig build test-cli
```

A new test file goes to `test/<group>/<name>_test.zig`, where `<group>` is one of `unit`, `golden`, `config`, `fuzz`, `integration`, or `cli`. The build discovers the test roots itself, so a new test file needs no `build.zig` edit.

## Security defaults

- Recursion is denied unless explicit client ACLs enable it; the process is not an open resolver by accident.
- Listeners use loopback/high ports by default. Privileged binding and non-loopback exposure require explicit configuration.
- No administrative socket or remote control plane is exposed.
- Forwarding is disabled by default and requires explicit recursion ACLs plus a configured forwarder.
- Full packet logging and secret/cookie logging are disabled by default.
- The Docker runtime is non-root.
- DNS semantics stay in this repository. Vetted crypto, TLS, HTTP, QUIC, or platform dependencies require a recorded dependency decision.
